# Gioka — sistema de cafetería

Monorepo npm workspaces: `server/` (Node 22+ + Express 5 + Postgres en Supabase vía `pg` + Supabase Realtime para eventos) y `client/` (Vite + React 19 + TS + Tailwind v4 + PWA). Se despliega en **Vercel** (`vercel.json`: front estático + `api/index.js` función serverless) o en un PC de la cafetería (`npm start`).

## Comandos
- `npm run dev` — server (3001, `--watch`) + client (5173, proxy a /api, /uploads)
- `npm run build` — build del client a `client/dist` (el server lo sirve en producción)
- `npm start` — server en producción en http://localhost:3001
- `python client/scripts/make-brand.py` — regenera assets de marca (`client/public/brand/*.png`) e íconos PWA/favicon a partir de `logo/*.png` (Pillow)

## Estructura
- `server/src/db.js` — pool `pg` (`DATABASE_URL` en `server/.env`), esquema Postgres (`initDb()` idempotente al arrancar), helpers async `get/all/run` (placeholders `?` → `$n`; `run` devuelve `lastInsertRowid` vía `RETURNING id`), `transaction(fn)` con AsyncLocalStorage (todo lo que se llama dentro usa la misma conexión), `localDay()/localHour()` para agrupar por día local, seed demo.
- `server/src/app.js` — la app Express (rutas, `/api/health`, `/api/realtime`, estático de `client/dist` solo fuera de Vercel) + `ready()` (initDb + bucket, una vez por proceso). `server/src/index.js` la levanta en HTTP (PC/LAN); `api/index.js` (raíz) la exporta como función de Vercel (`vercel.json` reenvía `/api/*` a ella y el resto a `index.html`).
- `server/src/realtime.js` — **eventos en vivo sin Socket.IO**: `emit(event, payload)` publica por REST en el canal `gioka` de Supabase Realtime (Broadcast API, `SUPABASE_SERVICE_KEY`); el navegador se suscribe con `SUPABASE_ANON_KEY` (la entrega `GET /api/realtime`). Eventos: `order:created`, `order:updated`, `stock:updated`, `stock:low`, `cash:updated` (payload envuelto en `{ data }`). Sin esas variables no hay eventos en vivo (Docker local). `server/src/bg.js` — `background(promise)`: en Vercel usa `waitUntil` (Telegram y Realtime terminan aunque la respuesta ya se envió).
- `server/src/storage.js` — `saveImage(dataUrl, name)`: sube a Supabase Storage (bucket público `gioka`, `SUPABASE_URL` + `SUPABASE_SERVICE_KEY`) o, sin esas variables, guarda en `server/uploads/`.
- `server/scripts/supabase-admin.mjs` — Management API (`SUPABASE_ACCESS_TOKEN`): `projects`, `keys <ref>`, `sql <ref> <query>`, `pooler <ref>`, `env <ref> <db_pass>` (escribe `server/.env`). Proyecto de producción: ref `orvreuhbpiatyqojedhi` ("giokacafeybakery", us-west-2), conexión por session pooler puerto 5432.
- `server/src/routes/*.js` — auth (email + contraseña, token en tabla `sessions`), catalog, orders (crea/paga/estado, descuenta stock por receta, emite socket), inventory, reports, settings, print (ESC/POS TCP 9100), cash (apertura/cierre de caja).
- `server/src/escpos.js` — builder ESC/POS sin dependencias + `receiptBuffer(order, settings, {kitchen})`.
- `server/src/telegram.js` — espejo de medios: `saveImage()` reenvía cada foto guardada al chat/canal de Telegram configurado en Ajustes (`telegram_bot_token` + `telegram_chat_id`, Bot API `sendPhoto`, fire-and-forget con `caption` HTML). `POST /api/settings/telegram/test` valida y manda un mensaje de prueba.
- `client/src/app/*` — PWA móvil de inventario (estilo iOS, `motion` para transiciones): `MobileShell` (tabs + AnimatePresence push/pop), `store.ts` (ítems unificados + borrador del ajuste `useFlow`), `ui.tsx` (Screen, Card, Thumb, BigButton…), pages Home/ItemDetail/Adjust/Confirm/Done/History/Alerts/Profile. Solo roles admin e inventario; `homeFor()` en `lib/nav.ts` decide el destino tras login (inventario → /app; admin en móvil/standalone → /app).
- `client/src/pages/*` — Login, Pos, Pedidos (KDS), Caja, Inventario, Admin, Reportes, Pantalla (público), Seguir (público, `/seguir/:code`).
- `client/src/components/FaceUnlock.tsx` — escáner estilo Face ID (Lottie `assets/face-unlock.json`, `lottie-web` build svg cargado bajo demanda, chunk `lottie`): intro → loop de escaneo (frames 27–72) → con `phase="success"` termina el barrido, dibuja el ✓ (hasta el frame 118) y llama `onDone`. Lo usa el modal de abrir caja.
- `client/src/components/Receipt.tsx` — impresión: modo `browser` (CSS 80mm + window.print) o `network` (POST /api/print/:id).
- `client/src/index.css` — tokens de diseño (`@theme`) y utilidades (`btn-*`, `card`, `input`, `pill`, `chip`).
- `client/src/lib/offline/*` — **capa offline-first**: `idb.ts` (IndexedDB: stores `cache`/`outbox`/`vault`/`meta`), `cache.ts` (última respuesta de cada GET, memoria + IDB), `queue.ts` (outbox de operaciones `Op` con UUID = `client_id`, persistida; `refOf/refPath` → `c_<uuid>` para entidades creadas offline), `project.ts` (proyecta las ops pendientes sobre cualquier GET: pedidos, productos/insumos con stock descontado, movimientos, caja), `net.ts` (estado online/offline: `GET /api/health` con backoff, eventos del navegador, socket, fallos de API), `sync.ts` (reenvía la cola en orden FIFO; 401 pausa, error 4xx marca la op como fallida y sus dependientes), `vault.ts` + `crypto.ts` (verificador local de contraseña, SHA-256 JS iterado, para login y apertura de caja sin conexión), `warm.ts` (precarga por rol), `boot.ts` (`initOffline()` desde `main.tsx`), `types.ts` (augmentación: `client_id/offline/pending`).
- `client/src/lib/actions.ts` — **todas las escritura de operación pasan por aquí**: `createOrder`, `payOrder`, `setOrderStatus`, `openCash`, `closeCash`, `adjustStock`, `createIngredient`, `login`, `logout`. Online y sin cola → envío directo (el servidor valida); si no → se encola, se aplica localmente y se emite el mismo evento que el socket (`order:created`, `stock:updated`, `cash:updated`) por `lib/offline/bus.ts`. Devuelven `{ result, queued }`.
- `client/src/lib/api.ts` — `api.get` cachea y proyecta (offline → caché o base vacía para listas); fallos de red/timeout/502-504/`db_offline` lanzan `OfflineError`. `lib/socket.ts`: `useSocket` escucha el canal de Supabase Realtime (`@supabase/realtime-js`, chunk `realtime`, se conecta al primer uso) **y** el bus local, más `sync:changed`; al re-suscribirse tras un corte emite `sync:changed` para que las páginas recarguen.
- `client/src/components/SyncStatus.tsx` — píldora flotante global (`OfflineBar` en `App.tsx`), botón con badge en la sidebar (`SyncButton`) y panel `SyncPanel` (pendientes/fallidas, reintentar, descartar). Perfil del app móvil muestra la tarjeta de sincronización.

## Convenciones
- UI en español. Roles: `admin` (edita todo), `cajero` (vende, cobra, caja; en pedidos solo marca **Entregado**; sin acceso a inventario), `cocina` (solo KDS: pendiente → preparando → listo), `inventario` (mueve stock y gestiona insumos; foto de comprobante obligatoria; sin acceso a pedidos/menú/reportes). Login email + contraseña (scrypt). Demo: admin@gioka.com/admin123, cajero@gioka.com/cajero123, cocina@gioka.com/cocina123, inventario@gioka.com/inventario123.
- Vender/cobrar exige caja abierta (`cash_sessions.closed_at IS NULL`); abrir caja requiere monto + email + contraseña del cajero (`POST /api/cash/open`). `client/src/components/OpenCash.tsx` centraliza el estado de caja (`useCashSession`).
- Fechas en DB en ISO UTC; agrupaciones por día usan `date(created_at,'localtime')`.
- Paleta de gráficos validada (dataviz): `#e0702f, #2b7fb8, #b8860b, #7d55d6, #2a8f68` en orden fijo.
- Sin dependencias nativas: `pg` es JS puro; no agregar módulos de impresora USB.
- **Vercel**: no hay proceso permanente ni disco → nada de WebSockets propios, timers globales ni escritura en `server/uploads` (Storage obligatorio); trabajo tras la respuesta siempre con `background()`. Límite de body 4,5 MB (las fotos van redimensionadas ≤1400 px). `TZ` debe fijarse en las variables de Vercel (las funciones corren en UTC y los reportes agrupan por día local). Usar el pooler de Supabase en modo transacción (puerto 6543) y `PG_POOL_MAX` bajo. La impresión ESC/POS por red no funciona desde la nube (el servidor no ve la LAN): modo navegador o servidor local. RLS está activo en todas las tablas (lo asegura `initDb`) porque la anon key viaja al navegador.
- **Offline**: nunca llamar `api.post/patch` para vender, cobrar, cambiar estado, caja o stock desde una página; usar `lib/actions.ts`. Los endpoints aceptan `client_id`/`op_id` (idempotencia) y `offline: true` + `created_at/at` (replay tolerante: mantiene hora, código y número del ticket si están libres; registra la venta aunque la caja esté cerrada o falte stock; `sessionAt()` liga el pedido a la caja abierta en ese momento). Ids `c_<uuid>` se aceptan en `/api/orders/:id`, `/api/inventory/adjust` y `/api/inventory/ingredients/:id`. `/api/health` devuelve 503 `db_offline` si Postgres no responde (pool con `connectionTimeoutMillis` y `query_timeout`); el error handler mapea errores de conexión a 503 `db_offline`. `POST /api/print/direct` imprime un pedido que solo existe en el dispositivo. El SW **no** cachea `/api` (lo hace la capa IDB).
- Rendimiento PWA: rutas con `lazy()` (la app móvil `/app/*` es un chunk propio en `client/src/app/routes.tsx`; `recharts` solo se descarga en Reportes), chunks `vendor/motion/charts/socket` fijos en `vite.config.ts`, `compression` + `Cache-Control: immutable` en el server, SW con CacheFirst para fotos (la API la cachea `lib/offline`). `useInventory` persiste el último snapshot en localStorage (abre al instante y revalida; funciona offline). En móvil evitar `backdrop-blur`/`blur-3xl` en superficies grandes (usar gradientes) y usar `will-change: transform` en lo que se anima.
- Todas las rutas son `async`; los flags `active/paid/track_stock` son INTEGER 0/1 en Postgres (se convierten a boolean al responder). Fechas en TEXT ISO UTC. Emails únicos por `lower(email)`.
- Para probar sin Supabase: `docker run -d -e POSTGRES_PASSWORD=test -e POSTGRES_DB=gioka -p 55432:5432 postgres:16-alpine` y `DATABASE_URL=postgres://postgres:test@localhost:55432/gioka`.

Después de CADA alteración al proyecto (código, docs, config), hacer commit y `git push origin main` sin que el usuario lo pida.
Remote: `https://github.com/giokacafeybakery/gioka.git` (rama `main`, repo privado). Cuenta con acceso: `stivencortez2026-afk` — si `gh auth status` muestra otra activa, ejecutar `gh auth switch --user stivencortez2026-afk` antes del push. - 2026-09-19 — **Deploy Vercel & Auth Fixes**: Se hizo público el repositorio en GitHub (ya que el plan Hobby de Vercel bloqueaba deploys de contribuidores sin permiso admin) y se arregló la autoría del commit (`git config user.email` de la cuenta principal de Vercel). Resolución del problema `tsc: command not found` en Vercel: al usar npm workspaces (`client/` y `server/`), la máquina de build de Vercel (por diseño en modo producción) fallaba sistemáticamente al instalar dependencias o crear los links de los binarios en `node_modules/.bin`, incluso pasando flags `NPM_CONFIG_PRODUCTION=false` y moviendo herramientas a `dependencies`. Solución final y definitiva a prueba de balas: el script de build en `client/package.json` se modificó a `"build": "npx --yes -p typescript tsc -b && npx --yes -p vite vite build"`, forzando a `npx` a localizar y usar los ejecutables correctos sin depender del enlazado de npm workspaces de Vercel.
- 2026-09-19 — **Corrección definitiva del build en Vercel**: el uso de `npx -p typescript` descargaba una versión flotante de TypeScript incompatible (`baseUrl` eliminado) y no resolvía los tipos de Vite/PWA instalados en el proyecto. `vercel.json` ahora instala explícitamente todos los workspaces con `npm install --include=dev --workspaces`; el cliente vuelve a ejecutar los binarios locales fijados por el lockfile (`tsc -b && vite build`), y `tsconfig.json` usa `paths` relativo sin `baseUrl`.
- 2026-09-19 — **Instalación Vercel aislada por paquete**: la instalación npm de la Vercel seguía omitiendo los binarios del cliente pese a `--workspaces` (solo instalaba 94 paquetes). `vercel.json` dejó de depender del hoisting del monorepo: instala `client` y `server` por separado con `--prefix ... --workspaces=false`, y ejecuta el build con `npm run build --prefix client`.
